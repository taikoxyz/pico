09 · direct peer channels

Two users open a channel between themselves — the hub only relays messages, it is never a party.

Why this exists

pico's default topology is 1-hop: every channel terminates at a hub, and payments flow client → hub → recipient. But the on-chain PaymentChannel is a generic two-party contract — userA and userB are just addresses, with no hub role baked in. A direct peer channel uses that fact: two users open a channel with each other, and the hub is demoted to a dumb message relay. No hub liquidity, no hub fee, no hub co-signing.

What was missing

The contracts and the off-chain state machine were already symmetric, so a direct channel was always possible on-chain. The gap was off-chain: the only way two parties exchanged signed states was through the hub's WebSocket server, and the "counterparty" co-signing logic lived only inside the hub. Direct channels add two pieces:

PieceWhere
relay envelopeThe hub forwards a relay{to, inner} message to the destination peer (queuing it if the peer is offline). It never reads or signs inner.
peer responderThe SDK ChannelClient in peerMode co-signs inbound payDirect, HTLC, closeRequest, and the open handshake — the role the hub used to play.
The relay is untrusted. Because the two peers co-sign each other's states directly, a malicious or buggy relay can stall or drop delivery, but it can never forge a state or steal funds. A misrouted message simply fails the recipient's signature check.

The flow

   userA (party)            hub (relay only)            userB (party)
        │                        │                          │
        │  subscribe(addr=A) ───▶│◀─── subscribe(addr=B)     │
        │  channelAnnounce ─────▶│ forward inner to B ──────▶│   B co-signs v1
        │◀───────── channelAnnounceAck (relayed back) ───────│
        │  htlcOffer / payDirect ▶│ forward ────────────────▶│   B settles / co-signs
        │◀────── htlcSettle / payDirectAck (relayed back) ───│

The opener (A) creates the channel on-chain, then sends a channelAnnounce carrying the channel record plus its half-signed v1 state. B verifies (optionally reading the channel on-chain), counter-signs, and replies — so the channel starts fully dual-signed on both sides. Payments and the cooperative close reuse the existing payDirect / HTLC / closeRequest messages; only the destination differs (a peer, not the hub).

Try it

Run a relay-enabled hub (HUB_ENABLE_RELAY=true), then, as two separate users sharing that relay URL:

# Bob: run the responder so he co-signs inbound peer messages
pico listen --peer --via ws://relay.example/ws

# Alice: open a direct channel with Bob (the hub is not a party)
pico channel open --peer 0xBob --amount 25 --via ws://relay.example/ws

# Alice: pay Bob's invoice directly (zero fee, no routing)
pico pay --invoice <bob-invoice> --peer --via ws://relay.example/ws

# Alice: cooperatively close, negotiated with Bob over the relay
pico channel close <channelId> --peer --via ws://relay.example/ws

Operators can confirm the relay is live with pico hub status <url>, or directly via GET /v1/info (advertises relay.enabled), GET /v1/stats (forwarded / queued counts), and the operator-gated GET /v1/relay/sessions.

Trade-offs to know

ConcernDirect peer channel
feesNone — there is no routing hop.
livenessThe responder peer must be online (running pico listen --peer) to co-sign, just as a hub must be up.
fraud watchingNo hub-side watchtower. Each peer must watch the chain (or run its own watchtower) to dispute a stale unilateral close. closeUnilateral / dispute work as usual.
fundingSingle-sided by default (opener funds, peer starts at 0). Dual-funded ERC-20 needs both parties to approve the contract.
discoveryOut of band for now: you pass --peer <addr> and --via <relay>. Nostr-based discovery is a later enhancement.
